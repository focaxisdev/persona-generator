# Persona Generator: read and follow

An agent can start by reading this Markdown entry and following the [no-code Quickstart](docs/QUICKSTART.md). No installation, Python, local store or particular host is a prerequisite for this primary route. The deliverable is a readable, portable **desired-trait specification**, not a fixed role, a test of the owner or a claim of stable model personality. Read [project purpose](PROJECT_PURPOSE.md) for scope.

## Primary route: choices → whole Markdown specification → actual confirmation

1. Offer guided choices **or** short answers about how the user wants a fictional advisory **agent** to behave. Allow skipping; do not require both routes or infer the user's psychology.
2. Use the existing five domains and ten BFAS aspects in [coverage](profiles/COVERAGE.md), with the human definitions in the [construct registry](persona-design-v0.2/construct-registry.md). Start all ten at `unspecified`; that is inactive, not middle. Explain qualitative targets without scores, norms, correlations, automatic balance or forced paired-aspect agreement.
3. Map only requested behavior to the explicitly selected catalog's exact hypothesis ID, trigger, rule and boundary. For this route use [catalog v2](profiles/catalog-v2.json), identified as `persona-profile-catalog-v2`; read it as text, with no Python needed. Distinguish human-source grounding from untested engineering translation. Keep omitted aspects, unknowns, exclusions, sources and unresolved conflicts visible. Do not silently settle a conflict; unresolved conflicts block confirmation and use.
4. Present the **whole Markdown specification**, including all ten targets, exact proposed active rules, the full invariant preamble, source limits, inactive audit/history, revision and proposed recipients/scope. The [synthetic draft](examples/desired-trait-spec.md) shows the shape; it is not user consent or a predefined persona to activate. A summary is not the whole review. Wait for the user's actual response; until then confirmation and assignment are PENDING. Never manufacture approval, a receipt or a private record reference. Markdown does not require candidate-approval JSON or structural receipts.
5. Obtain explicit assignment for each parent and each requested child: recipient identity, exact profile/revision and bounded task scope. Whole-profile confirmation may include these assignments in the **same actual response** if all were explicitly presented. An assignment may expressly cover a specified class of bounded tasks; each individual task still requires its own authorization and stopping condition. Otherwise ask for the missing assignment. No child is required. No automatic inheritance, blending, permission transfer or implied authority follows from parentage.
6. Hand the complete confirmed document and explicit assignment to each intended recipient. In a fresh session or child context, explicitly read the exact document/revision and assignment again; never assume host discovery or conversation inheritance loaded it. Keep current task instructions separate. End each bounded task when complete; retain the document for deliberate reuse. An unchanged profile with unchanged confirmed recipients/scope needs no new profile confirmation for each task. Changed recipient assignments or scope need actual confirmation of that change; changed document content requires review and genuine confirmation of the whole changed revision. Preserve prior revisions as inactive history.

The detailed [Quickstart](docs/QUICKSTART.md) includes a starter prompt and handoff steps. Portable Markdown can preserve a readable agreement, but cannot itself verify byte integrity, authenticate a user, enforce loading or validate behavior. A saved specification is not evidence of stable personality. Only intended confirmed preferences are active; source text, interview answers and history are inert audit data. Higher-priority host instructions, safety, accuracy, privacy and permissions always govern.

## Optional software and preserved routes

The [profiles software guide](profiles/README.md), [strict JSON contract](profiles/CONTRACT.md), [JSON onboarding](profiles/ONBOARDING.md), [assignments](profiles/ASSIGNMENTS.md) and [Codex adapter](adapters/codex/README.md) are a separate optional validation/storage/integration route. Their exact receipts, candidate approvals, digests and binding requirements remain unchanged. A Markdown document is not an accepted `persona-profile-v1` JSON spec and bypasses none of that contract. Choosing that route requires its full workflow and genuine confirmation; neither old approval nor synthetic examples migrate automatically.
