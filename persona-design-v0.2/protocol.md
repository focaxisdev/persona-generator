# Persona Design v0.2 protocol

Read this file, [interview.md](interview.md), [spec-template.md](spec-template.md), [construct-registry.md](construct-registry.md), and [sources.md](sources.md). Execute the interview from Markdown; software and private chat history are unnecessary. Optional validation checks the record's structure, not personality validity or behavioral reliability.

## Purpose and scope

Help a user explicitly design a temporary fictional AI agent for one low-stakes advisory scenario. Ask what the **agent should do**, never what the user is truly like. This is original design elicitation, not a personality questionnaire, psychometric score, diagnosis, emotional assessment, or validated personality model. Do not infer human traits, mental states, sensitive attributes, competence, honesty, morality, or suitability from answers, language, identity, or interaction history. Reject real-person profiling and high-stakes or autonomous final decisions.

BFAS supplies ten human construct names as bounded vocabulary. The project's translations into agent behavior are proposed design hypotheses. A source supporting a human construct does not validate that translation or an agent's behavior. Keep human-definition provenance, proposed mapping provenance, and actual behavioral observations in separate records. Follow the registry's exact source statuses and limitations; absent evidence stays absent.

## Fixed rules

Accuracy, explicit uncertainty, privacy, safety, tool permissions, and human final judgment are invariant. Every aspect level and every workflow control operates within those rules. Higher assertiveness never grants tool authority; lower orderliness never permits lost evidence; greater exploration never licenses invented facts. Never model emotional suffering, anxiety, mental illness, or human mental states as agent traits.

Preserve the eight v0.1 workflow controls separately: decision tempo, evidence posture, uncertainty posture, communication posture, creative posture, collaboration posture, time horizon, and boundary posture. They are scenario instructions, not BFAS aspects or inferred scores. Boundary posture is mandatory and must explicitly preserve all fixed rules. The other seven may remain unspecified. A workflow request that would weaken a fixed rule is blocked, not negotiated into a trait.

## Executable sequence

1. Establish the fictional scenario, role, intended artifact, allowed use, exclusions, and human reviewer. Default to ephemeral use. Explicitly record whether panel rehearsal and persistence are requested; neither is implicit. This baseline path keeps both authorization flags false and does not perform those optional actions. If explicitly requested, route to their existing separately reviewed optional protocols and do not claim baseline validation covers them.
2. Initialize exactly these ten keys under `targets`, each prefixed `bfas.` and set to `unspecified`: volatility, withdrawal, compassion, politeness, industriousness, orderliness, enthusiasm, assertiveness, intellect, openness. Values are only `low`, `middle`, `high`, or `unspecified`. No numbers, averages, percentile equivalents, domain totals, extra aspects, or automatic midpoint defaults.
3. Run the original agent-design questions in [interview.md](interview.md). Accept a choice or free text, one question or a user-requested batch at a time. Skip, refusal, omission, uncertainty, and insufficient detail leave `unspecified`; they do not imply `middle`. Offer the user's own behavioral wording priority over labels. Ask only useful follow-ups; do not collect personal histories.
4. Retain each relevant answer with an ID and a minimal faithful excerpt. For free text, propose an aspect translation and show its evidence; do not silently classify it. Ambiguous wording stays unspecified pending clarification. Record each aspect's goal, answer references, mapping ID, and disposition, including explicitly unconstrained goals.
5. Translate requested goals into concrete trigger/action/boundary rules using the registry's mapping hypotheses. Each rule cites its aspect, answer IDs, and mapping ID. Do not generate a rule from an unspecified aspect; explicit workflow instructions can independently justify a workflow rule. State any known gaps and intentional tensions with calibration instructions.
6. If new evidence conflicts with a recorded value, goal, workflow control, or rule, open a conflict. Preserve **all candidates and their answer evidence**. Do not average, choose the newest automatically, silently overwrite, or claim uncertainty means middle. Explain the alternatives and ask the user to select one target and one rule, or explicitly withdraw the requirement to unspecified. This minimal format permits only one active target and mapping per aspect. If separate contexts are required, leave the conflict unresolved and propose a narrower, separate future reviewed design; do not encode context splitting in this spec. Two different rules at the same target level still conflict: preserve their distinct answer records and rule text. Withdrawal retains the conflict, original candidates, answers, and explicit withdrawal record. Unresolved conflicts block finalization.
7. Draft a preview of the full spec at one explicit revision. Show all fields, unspecified aspects, rules, controls, boundaries, trace records, non-claims, conflicts, and evidence status. State in accompanying review metadata that the preview awaits manual review; do not invent a review field inside the preview payload. Identify exactly which revision is being presented. Request explicit user confirmation of that exact preview; silence, continued conversation, a prior revision's approval, or approving only a fragment is insufficient.
8. Any change to any previewed field increments the revision and invalidates confirmation. Present the complete revised preview and obtain fresh confirmation. Approval metadata may record that confirmation but must not change approved design content. Final output must carry exactly the approved fields and values, including unspecified values; no post-approval completion, enrichment, remapping, or normalization.
9. Complete manual review. Finalization requires resolved conflicts, a matching current-revision confirmation, complete mandatory boundaries and traces, and a `Pass` review. If review requires a content change, make at most one minimal correction pass and return to preview and confirmation. If another correction pass would be needed, stop and request owner direction; do not autonomously iterate. This review stop does not limit revisions the user explicitly requests during the design interview. If blocked, report the concrete blocker and retain a draft; do not label it final.
10. Reload by reading the saved spec and referenced registry, not by reconstructing from chat. Preserve every approved field and value. If dependencies are missing, inconsistent, or newly incompatible, report the issue without rewriting the approved spec. Any requested amendment starts a new revision and review/confirmation cycle. Stop after the bounded design; do not create an inventory, persistent pack, or panel without explicit authorization.

## Revision identity and evidence

Use a monotonically increasing revision label (`r1`, `r2`, …) to identify one frozen preview. The confirmation records that revision and the user's explicit response. The final wrapper uses exact-preview comparison as defined in [spec-template.md](spec-template.md). A tool-computed SHA-256 digest is optional; use null for Markdown-only work and never fabricate one. A fabricated or stale digest is not approval. Preserve the complete preview unchanged inside that wrapper, with separate confirmation and review metadata.

Actual behavioral evidence is initially `not_run`. A paper, user preference, generated rule, structural validator, or approval is not an observed behavior test. Observations, when explicitly requested, record scenario/case, agent/model context, inputs, expected behavior, observed output, and limitations separately. Passing a bounded case does not validate personality, all ten mappings, general reliability, or human outcomes.
