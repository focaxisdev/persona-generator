# Persistent profile v1 candidate contract

`persona-profile-v1` is a separate, unreleased desired-behavior contract for fictional, low-stakes advisory agents. It is not `persona-core-v1`, an automatic upgrade, a human assessment, a model behavior result, or evidence transferred from historical mappings. Its 30 anchor rules are original **untested engineering hypotheses**. The frozen source registry provides BFAS vocabulary only. All ten aspects permit independently selected `low`, `middle`, `high`, or `unspecified`; there is no normalization, forced balance, averaging, default middle or assumed correlation. Middle is an explicit design choice. Every unspecified target emits no active preference instruction.

The compiler performs local standard-library operations only. It imports strict JSON parsing/canonical hashing primitives from `core.compiler`, not its validator, catalog or renderer. Core source, its two-operation contract, historical mappings, request envelope and paused evaluation records remain separate. This profile compiler makes no experimental calls and cannot certify persistence of behavior in a model.

## Exact preview and confirmation

A preview has exactly `schema_version`, `kind`, `profile_id`, `revision`, `catalog`, `sources`, `targets`, `mappings`, `answers`, `approvals`, `conflicts`, `blocking_issues`, `unknowns`, `history`, `evidence`. Version is `persona-profile-v1`, kind is `preview`. Profile and agent IDs match `[A-Za-z0-9][A-Za-z0-9_.-]{0,79}`; revision matches `r[1-9][0-9]*`. The profile ID is stable across revisions, never an inferred identity. `catalog` has exactly `id` and `sha256` and must match the compiler's trusted catalog bytes. `sources` is the exact ordered catalog dependency list of frozen source paths and SHA-256 hashes. The compiler independently pins the two paths and hashes and rechecks them on every load. Paths and source-ledger version names identify the source versions; updates require a reviewed catalog/compiler change and new confirmation.

`targets` contains exactly all ten existing `bfas.*` aspect IDs. Each active target needs one and only one mapping. A mapping has exactly `id`, `aspect`, `anchor`, `trigger`, `rule`, `boundary`, `answer_ids`, `approval_id`; its ID is `hyp.<aspect-name>.v1`. Its complete trigger, rule and boundary must equal the selected catalog anchor. Unknown IDs, stale wording, custom prose, mappings for unspecified targets, duplicates and missing active mappings fail closed.

Answers have exactly `id`, `origin`, `kind`, `text`, `record_ref`. Origins are `owner` or `synthetic_fixture`; kinds are `choice` or `short-answer`. Approvals have exactly `id`, `answer_id`, `aspect`, `anchor`, `candidate_sha256`; the digest covers exactly `{id,aspect,anchor,trigger,rule,boundary}` from that candidate. The answer must exist and appear among the mapping's answer IDs. Every approval must be used. These are recorded structural assertions, never an approval action or authentication. The compiler does not infer a target from answer text. `unknowns` and `history` are arrays of audit strings. Answers, record references and all audit text remain inert, even if written as commands. `evidence` remains exactly `{status:"untested",behavioral_validation:false}`.

A confirmed spec has exactly `schema_version`, `kind` (`spec`), `approved_preview` (the entire unchanged preview), `confirmation`, `review`. Confirmation has exactly `status` (`confirmed`), `profile_id`, `revision`, `snapshot_sha256`, `presented_file_sha256`, `effective_sha256`, `record_ref`, `confirmed_by`, `origin`. Its profile/revision must match, snapshot digest binds the complete canonical preview, presented digest binds the exact separate UTF-8 preview bytes, and effective digest binds exact UTF-8 renderer output. The presented file must parse to the full embedded preview. JSON whitespace changes alter the presented-byte binding. Canonical hashing uses the core package convention of sorted keys, compact JSON, UTF-8, `ensure_ascii=False`, `allow_nan=False`; it is not a claim of RFC 8785 compliance.

Review has exactly `status` (`Pass`) and nonempty `record_ref`. Any preview change, including revision, target, answer, audit text or dependency hash, requires a new full-preview confirmation. The compiler never auto-confirms or auto-reviews. Structural fields cannot authenticate an owner, reviewer, record reference, consent or the truth of a declaration. Synthetic answers cannot support a confirmation labeled `owner`. The supplied fixture builder fabricates explicitly labeled **synthetic format examples**, not authentic owner actions.

Unknown or missing fields, wrong types, duplicate JSON keys at every depth, malformed Unicode, nonfinite numbers, float overflow, multiple documents and narrative outside an optional single whole-document JSON fence are rejected. No role, capability, tool, value, state, account or permission fields are accepted as traits.

## Conflicts and projection

A conflict has exactly `id`, `aspect`, `candidates`, `status`, `selected_candidate_id`, `resolution_answer_id`. At most one exists per aspect. Each candidate has exactly `id`, `anchor`, `trigger`, `rule`, `boundary`, `answer_ids`; at least two distinct catalog anchors are required, with complete exact catalog wording and valid answer references. An `unresolved` conflict retains null selection/resolution fields and blocks confirmation validation, publication and rendering. `validate-preview --inspect-unresolved` permits structural inspection and reports `blocked_by_unresolved:true`; it produces no executable projection. A `selected` conflict names a candidate whose anchor, exact wording and answer IDs match the active mapping; the resolution answer must be the mapping's approval answer. A `withdrawn` conflict has null selection, leaves the target unspecified, and references a recorded resolution answer. A boolean “resolved” flag alone cannot bypass these checks.

Manual cross-aspect, host-constraint or other semantic problems are retained in `blocking_issues`, an array with exact fields `id`, `description`, `answer_ids`, `status`, `resolution_answer_id`, `resolution`. The original description and nonempty valid answer references stay audit data. `unresolved` requires null resolution fields and blocks spec validation, publication and every reload/render; preview inspection can retain it through `--inspect-unresolved`. `resolved` requires an existing resolution answer (with its validated origin and record reference) and nonempty resolution explanation. Resolving an issue or changing any issue text changes the full snapshot and requires new confirmation. A record is a reviewable assertion of resolution, not evidence that a semantic problem actually disappeared. This compiler cannot discover omitted issues or prevent a dishonest author deleting history and obtaining a fresh structural receipt. Issue and resolution prose never becomes a rule.

The catalog additionally supports declared `constraints` records `{context,action,effect}` on anchors. The limited detector rejects opposite `require`/`forbid` effects for the exact same context and action among active rules. Current catalog anchors declare empty constraint lists; the compiler does **not** solve prose semantics, discover every contradiction or diagnose an unusual combination as conflicting. Explicit unresolved conflicts remain blocked regardless of that detector. See [coverage](COVERAGE.md) for slot separation and interactions.

Only the trusted catalog preamble and exact active trigger/rule/boundary text enter renderer output, sorted by hypothesis ID. Labels, provenance, answers, approvals, conflicts and audit text do not. The invariant preamble applies even when every target is unspecified: host instructions, current task constraints, facts, calibrated uncertainty, safety, privacy, tool permissions and human final judgment retain priority. Roles, capabilities, values, transient state and permissions belong to the host separately. A temporary bounded-task request can override a preference within that request; it does not mutate the persistent profile. The compiler does not call or control a host/model and does not authenticate that a caller kept task text separate.

## Immutable storage and explicit per-agent binding

`publish` accepts already confirmed spec and separately preserved presented preview. It stores `versions/<profile_id>/<revision>/{spec.json,presented.json,manifest.json}` in a caller-selected directory. A revision cannot be overwritten, even identically, and a new revision must advance beyond existing revisions for that profile. The manifest binds profile/revision, snapshot, effective, catalog and complete canonical spec digests plus exact stored spec/presented byte hashes. Every reload revalidates schema, dependencies, confirmation, presentation, renderer digests, identity and manifest. Store symlink paths and path-like IDs are rejected. This is local tamper detection against retained pins, not a signature, hostile-filesystem sandbox, encrypted store or protection against an actor rewriting the entire store and its bindings. A concurrent writer or interrupted publish may leave a rejected partial revision requiring manual repair; publication is not a transactional database.

A binding is a strict `persona-profile-binding-v1` object with exactly `agent_id`, `profile_id`, `revision`, `snapshot_sha256`, `effective_sha256`, `catalog_sha256`, `spec_sha256`, and `schema_version`. Bind requires the caller to supply the exact profile revision and snapshot/effective digests; it never resolves “latest.” Every agent needs its own binding lookup using its own agent ID. A parent and two children may bind the same or different confirmed revisions. No binding is copied or inferred from a parent, and there is no merging, averaging or fallback. Rebinding one child does not alter another child, its parent, the profile revision, or any host account configuration. A new persistent revision requires new confirmation followed by an explicit rebind; old bindings keep their old revision. Binding replacement is local and deliberate. Tools/roles/state are never inferred from a binding.

## Public API and CLI

Python API: `preview_receipt(presented_bytes,repo_root=None,allow_unresolved=False) -> draft review digests`, `load_catalog(repo_root=None)`, `validate_preview(preview,repo_root=None,allow_unresolved=False)`, `validate_spec(spec,presented_bytes,repo_root=None) -> exact rendered text`, `validate(spec_path,presented_path,repo_root=None) -> (spec,presented_bytes,text)`, `publish(spec_path,presented_path,store,repo_root=None) -> pin`, `load_version(store,profile_id,revision,repo_root=None) -> (spec,text)`, `bind(store,agent_id,profile_id,revision,snapshot_sha256,effective_sha256,repo_root=None) -> binding`, `load_binding(store,agent_id,repo_root=None) -> (binding,text)`. `ProfileError` is the reused `CoreError`/`ValueError` exception class. `_render` is an internal formatter, not an approval validator; external callers must use validating entry points.

`validate-preview` reads the exact input bytes and returns draft `snapshot_sha256`, `presented_file_sha256`, `effective_sha256`, profile/revision/catalog identity, `validation_status:structural_only`, `confirmation_status:NOT_CONFIRMED` and unresolved-block status. It emits no active instructions and never creates approval or confirmation. With `--inspect-unresolved`, unresolved drafts retain null `effective_sha256`; they cannot be published. Preserve the complete presented bytes, obtain actual owner confirmation and review, then copy the exact draft hashes into the manually recorded spec confirmation. Re-run draft review after any edit.

`python -m profiles validate-preview PREVIEW [--inspect-unresolved]`, `validate SPEC --presented PREVIEW`, `publish SPEC --presented PREVIEW --store ABS`, `bind --store ABS --agent ID --profile ID --revision rN --snapshot SHA --effective SHA`, `load --store ABS --agent ID`, and `render --store ABS --agent ID` are supported. JSON outputs are audit data; only `render` stdout is the exact instruction payload. Rejection exits 2 with `REJECTED` on stderr. Loading/publishing are local persistence actions, not installation or activation. The optional [Codex adapter](../adapters/codex/README.md) owns host-specific invocation and installation boundaries.
