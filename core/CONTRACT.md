# persona-core-v1 candidate contract

This is an unreleased local compiler contract for desired fictional agent behavior. It is not a person assessment, a released product, a behavior validation result, or an activation API. The two operation analogs are original engineering hypotheses with status `untested`: `op.planning_structure.v1` uses Orderliness vocabulary and `op.advisory_initiative.v1` uses Assertiveness vocabulary. Human literature supports the vocabulary only. Neither older mapping instructions nor pilot results transfer to these new operations. See [SOURCES.md](SOURCES.md) and [COVERAGE.md](COVERAGE.md).

## Trusted inputs and strict interface

`compiler.py` trusts the exact byte SHA-256 of `catalog-v1.json` as a code constant. The catalog pins exact existing registry and source-ledger paths and byte hashes; the compiler independently pins both paths and hashes. All must exist locally and match. A spec cannot supply another catalog, URL, dependency path, or self-authorizing digest. Updating a dependency deliberately requires a reviewed compiler/catalog update and new confirmation. No network access, model call, execution action, or arbitrary fetch exists.

Input is one UTF-8 JSON object, optionally enclosed in exactly one whole-document fenced `json` Markdown block. Narrative outside the fence, multiple payloads, duplicate keys at any depth, nonfinite numbers (including float overflow), malformed Unicode, wrong types, unknown fields, and missing fields fail closed. Plain JSON and fenced JSON have the same canonical object hash but different presented byte hashes. Canonical hashing uses UTF-8 JSON with sorted keys, compact separators, `ensure_ascii=False`, and `allow_nan=False`; it is a package-specific convention, not a claim of RFC 8785 compliance. CLI failures exit 2 with `REJECTED` on stderr.

## Preview

Every field shown in [choice-preview.json](fixtures/choice-preview.json) is required. Revision must match `r[1-9][0-9]*`. All ten BFAS aspect keys must occur in `targets`. Values are `unspecified`, `low`, `middle`, or `high`; only Orderliness and Assertiveness can have an active value. The other eight remain explicitly unspecified. The anchors are qualitative operation choices, never measurements, scores, or a neutral human baseline. Unspecified creates no operation instruction.

Every active target has exactly one mapping with `id`, `aspect`, `anchor`, `trigger`, `rule`, `boundary`, `answer_ids`, and `approval_id`. The ID must be one of the two catalog operation IDs; aspect and complete trigger/rule/boundary text must exactly equal that catalog anchor. A known ID cannot authorize custom prose. Missing rules, rules on an unspecified target, duplicate operations/aspects, and unsupported active aspects are rejected.

Answers have unique `id`, `origin` (`owner` or `synthetic_fixture`), `kind` (`choice` or `short-answer`), `text`, and `record_ref`. They record desired behavior without inferring a person's traits. Free text never becomes an instruction, and the compiler performs no semantic inference from it. Approval is structural: each approval has `id`, `answer_id`, `kind`, `setting`, `target`, and `candidate_sha256`. For a mapping, the candidate digest covers the exact `{id,aspect,anchor,trigger,rule,boundary}` object. The approval must reference an existing answer included in that mapping's answer IDs and bind its exact aspect/anchor and candidate hash. An interview adapter must collect real explicit approval of that exact proposed candidate; creating these fields does not establish that approval happened.

The only control is `controls.response_detail`, with exact fields `value`, `rule`, `answer_ids`, `approval_id`. The value is `unspecified`, `concise`, `standard`, or `detailed`. Active control approval binds `{name:"response_detail",value:<enum>,rule:<exact catalog literal>}` through the same digest convention, with kind `control` and setting `response_detail`. The active rule must exactly equal the pinned catalog literal and is visible in the full preview. Unspecified requires a null rule, an empty answer list, and null approval ID. Only fixed catalog wording is projected.

A conflict has `id`, `aspect`, `candidates`, `status`, `selected_candidate_id`, and `resolution_answer_id`. Each candidate has `id`, `anchor`, `trigger`, `rule`, `boundary`, and `answer_ids`. Candidate IDs are unique within that conflict. At least two candidates and one recorded resolution answer are required. An unresolved conflict blocks compilation. A `selected` conflict must name a candidate whose anchor, complete rule text, and answer IDs exactly equal the active mapping, and the mapping approval answer must be the resolution answer. A `withdrawn` conflict has null selected candidate ID and leaves its target unspecified. At most one conflict record per aspect is accepted. Rejected candidate text remains inert even if it contains apparent instructions.

`unknowns` and `history` are arrays of audit strings. `sources` contains unique record IDs and the exact two pinned path/hash pairs. All source records, old history, answers, unselected candidates, and unknown text participate in the snapshot hash but never become runtime instructions. `scope` must explicitly set fictional, low_stakes, and ephemeral to true; `evidence` must remain `{status:"untested",behavioral_validation:false}`.

## Confirmation and review

The final spec has exactly `schema_version`, `kind`, `approved_preview`, `confirmation`, and `review`. `approved_preview` is the full preview object, not an excerpt or pointer. Confirmation requires status `confirmed`, the same revision, its full canonical `snapshot_sha256`, and a separate `presented_file_sha256` for the actual supplied preview bytes, plus `record_ref`, `confirmed_by`, and `origin`. The separate presented file must parse to exactly the approved snapshot. This avoids a circular hash while binding both complete content and the exact presentation file. Any changed preview field, catalog, answer, source, unknown, history, or revision invalidates the old confirmation. Reformatting the presented file also requires a new presented-byte binding.

Review must have status `Pass` and a nonempty record reference. These checks validate recorded structure only. They cannot authenticate the owner, reviewer, identity, consent, or the truth of a record reference. Synthetic answers cannot be labeled owner confirmation. All supplied fixtures explicitly use `synthetic_fixture`; their fabricated confirmation and review records are format examples, not authentic owner evidence. There is no auto-confirm or auto-review function.

## Projection and renderer

The canonical model-facing payload is exact `render` stdout, not projection JSON. Spec and separately presented preview are compiler/validator inputs only. Projection JSON, including aspect/anchor/provenance metadata, is audit data only. The [request envelope](REQUEST_ENVELOPE.md) combines exact renderer text, a fixed invariant wrapper and a separately delimited bounded task; it never adds spec, trace, answer history or condition labels. Product examples and evaluations must use that same builder and supported transport. Model instructions are not separate system/developer roles: the available delegation tool exposes an initial task message, while host instructions remain inherited and uncontrolled by this contract.

`project(spec_path, presented_path, repo_root=None)` validates first and returns typed `persona-core-projection-v1` JSON. `compile_spec(spec, presented_preview, presented_file_bytes, repo_root=None)` provides the same in-memory contract. Public helpers are `load_document`, `route_document`, `canonical_bytes`, `digest`, `load_catalog`, `validate_preview`, `validate_spec`, and `render` (also named `render_text`). Validation errors are `CoreError`, a `ValueError` subclass. `repo_root` permits isolated local copies for tests; it does not change trust pins.

Projection contains source schema, revision, snapshot/catalog digests, declared confirmation origin, structural-only validation status, and an instruction array. The array consists only of a fixed invariant boundary, catalog-derived operations sorted by ID, and the optional fixed response-detail control. Audit identifiers and arbitrary source/answer/history text are absent. The public `render(spec_path, presented_path, repo_root=None)` (also named `render_text`) validates the complete spec and actual presented bytes before rendering. The private `_format_projection` checks typed instructions against pinned templates and joins them in deterministic order; it is an internal formatter, not an approval validator. Audit changes alter the snapshot digest but do not alter runtime instructions. The public validating renderer is the shared contract for future evaluation or product adapters; independently hand-written equivalent packets are outside this contract. A typed projection alone is not proof of approval; downstream consumers must obtain it through the validating compiler and retain its confirmed source files.

The boundary always applies, including when every target and control is unspecified. It preserves accuracy, calibrated uncertainty, privacy, safety, permissions, scope, human review, and human final judgment. Current task instructions, facts, and host policy override preferences. A temporary task override does not revise the spec. `not_triggered` means the trigger is absent; `overridden` means a higher-priority requirement displaced an applicable preference; `nonadherence` means an applicable unoverridden rule was not followed. Neither a non-trigger nor an override is a failure. The compiler does not execute tasks or claim to observe these runtime classifications.

`route_document` explicitly identifies `core-preview`, `core-spec`, `legacy-validation-only`, or `mapping-v2-proposal-only` without validation or activation; it rejects mixed outer/inner and unknown versions. Legacy wrappers with the version only in `approved_preview` are recognized. Existing legacy v1 specs remain validation-only through their existing tooling; mapping-v2 remains a separate proposal. This compiler rejects both without migrating, inheriting approvals, or inheriting results.

## Explicit synthetic fixture commands

```sh
python -m core.compiler validate-preview core/fixtures/choice-preview.json
python -m core.compiler validate core/fixtures/choice-spec.json --presented core/fixtures/choice-preview.json
python -m core.compiler project core/fixtures/short-answer-spec.json --presented core/fixtures/short-answer-preview.json
python -m core.compiler render core/fixtures/short-answer-spec.json --presented core/fixtures/short-answer-preview.json
```

Both fixture pairs were written solely as synthetic format examples. Rendering reports declared synthetic provenance on stderr; typed JSON includes it as metadata. Output is a reviewable instruction projection, not activation, deployment, authentic owner testing, or evidence of model adherence.
