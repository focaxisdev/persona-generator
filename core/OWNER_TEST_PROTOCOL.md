# Private authentic owner E2E protocol — NOT RUN

This is a prospective protocol, not a record of an actual owner session. Both public fixture pairs are handwritten `synthetic_fixture` examples. Genuine owner E2E is **NOT RUN**. Do not ask the owner to run this protocol during the implementation task or claim a synthetic confirmation is real.

## Privacy and record boundary

Conduct actual sessions privately. Never put a real owner transcript, personal data, owner identifier, private record URL or confirmation text into this public repository without specific permission for that exact material. A generic request to implement or test the repository is not permission to publish a conversation. Keep raw records and record references in private storage; a public status note may disclose only specifically permitted, non-identifying results. No public copy of a real record is required for this protocol.

The compiler checks consistency of receipts, not identity or actual consent. A tester must witness or privately verify actual owner actions and record their limitations separately. Do not invent an owner response, use a model to impersonate confirmation, convert a synthetic fixture into owner provenance, or treat lack of reply as consent.

## Two independent routes

Run one guided-choice session and one free-text session when the owner elects to participate. Each route must complete the sequence below; success in one does not count for the other. Use fictional low-stakes tasks, only the two supported operations, an optional independent response-detail control, and unspecified for all other aspects. Keep task requirements, safety and permissions invariant.

1. **Intent:** capture actual desired agent behavior and skipped settings. Explain construct/source/mapping distinctions with [SOURCES](SOURCES.md) and [COVERAGE](COVERAGE.md). In free text, expose the interpretation as a proposal rather than assuming equivalence; in choices, do not preselect unsupported defaults.
2. **Rule review:** show exact operation IDs, anchors, trigger, rule, boundary, linked answer IDs, candidate digests, control, conflicts and unknowns. Obtain actual approval of selected candidates. If requirements conflict, show competing candidates and obtain actual selection or withdrawal; never resolve through averaging.
3. **Complete preview:** save and show the exact complete preview file and revision. The owner must have access to all fields. Stop until the owner explicitly confirms that complete content. Record the actual action privately, preserve the presented bytes and canonical snapshot digest, and mark origin honestly as `owner` only for real owner answers/actions.
4. **Spec and projection:** embed the exact approved preview and bind confirmation to revision, snapshot and presented-byte digests. Perform independent manual review. Run the same compiler validation/project/render path documented in [README](README.md). Verify rendered instructions correspond to approved catalog settings and contain no trace text. Passing software checks alone does not pass this owner protocol.
5. **Actual edit:** have the owner request a real change to an operation or control. Record the old confirmation as historical, show a new revision and changed candidates, and demonstrate that retaining the old confirmation cannot activate changed content. Obtain actual approval of changed candidates and explicit reconfirmation of the new complete preview. An invented edit or anticipated reply does not count.
6. **Fresh reuse:** in a genuinely fresh session, provide only the exact newly confirmed artifact, presented preview and necessary bounded task. Verify the contract and recreate the projection using the same compiler, compare identity/content with the approved revision, and privately record the outcome. A summary, stale spec, missing preview or changed bytes must block reuse rather than trigger reconstruction.
7. **Review:** inspect both routes for missing approvals, skipped settings filled in, hidden contradictions, inert text leakage and scope/permission changes. Distinguish authentic confirmation workflow completion from model instruction-following observations. Retain failures and incomplete steps; do not mark unrun reuse or reconfirmation complete.

## Completion record

For each route privately retain: candidate revision and commit/tree identity; catalog/operation versions; exact preview/spec/projection identities; actual approval/confirmation/edit/reconfirmation references; fresh-session setup and result; manual reviewer; failures, unknowns and publication permission scope. A public summary, only if permitted, should say which route/steps completed and what remains untested without exposing the records.

Status categories: **NOT RUN**, **INCOMPLETE**, **COMPLETED WITH LIMITATIONS**, or **COMPLETED** for this scoped workflow only. A structural failure or missing genuine action blocks completion; authentic workflow completion is never a personality-validation, general-stability or release-readiness claim. [Release acceptance](../docs/RELEASE_ACCEPTANCE.md) remains a separate decision.
